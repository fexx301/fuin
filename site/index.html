    04 · How it works

    Seal, run, commit, close, sample, reveal, verify.

    Each step leaves evidence a stranger can check. The NEAR registry contract has no access keys, so nobody can rewrite it.

    What a VERIFIED certificate proves

    • A named model's attested TEE key signed every committed answer, byte for byte.
    • The test set and policy were sealed on NEAR before the results were committed.
    • A future NEAR block, not the owner, picked the audited items.
    • The revealed answers re-score to the committed scores: 95% detection power for ≥10% wrong scores.
    • The serving container and weights trace to NEAR's public deployment repo.

    What it doesn't prove

    • Hidden scores are checked statistically, not item by item.
    • Instances of a model can share a key; the trace is taken at preflight.
    • Discarded or uncommitted runs can't be seen. Committed runs are numbered.
    • Reveals permanently disclose their questions: 24 of round 1's 60 (one indirectly), 23 of round 2's 60, 28 of round 3's 300.
    • When inference happened. Testnet only.

    05 · Refusals

    14 tests of tampering, unsupported models and missing evidence.

    Each fixture makes one change to a real certificate, or withholds a service the verifier needs. The command-line verifier must give exactly this verdict, at the check that catches it. scripts/review.sh runs them all.

    06 · Reproduce

    Check everything on your own machine.

    No account, no API key, no test set. About five minutes.

    # every certificate, all 14 fixtures and the tests
git clone https://github.com/fexx301/fuin && cd fuin
./scripts/review.sh

# one certificate, with every check printed
env -u NEARAI_API_KEY uv run fuin verify examples/cert-near-dev-60-r2-glm-5.3-flash.json

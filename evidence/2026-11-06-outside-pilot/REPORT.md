## What was confusing or broke (in the order it happened)

1. **PILOT.md assumes macOS or Linux; the machine was Windows (13:16).** I used WSL2 Ubuntu 24.04 because PILOT.md lists only macOS and Linux. Cost: a few minutes to decide. Not a defect, but there is no Windows guidance.
2. **None of the prerequisites were present in WSL (13:20 to 13:32).** `uv`, Rust, `gh` and `near` were all missing, and there was no passwordless `sudo`. I installed `uv` and Rust with their official scripts and downloaded the `gh` binary into `~/.local/bin`. The user ran the root `apt` step. Cost: about 15 min for the downloads and the apt step (exact time not recorded).
3. **`cargo install --locked near-cli-rs` failed (started about 13:32, failed 13:44:51).** The `hidapi` build script reported `Unable to find libudev`. PILOT.md does not mention system packages. Fix: `apt-get install -y libudev-dev`, then rerun the same cargo command (finished 14:04:27, about 19 min of compiling). Cost: about 12 min for the failed build plus the rebuild. Linux users need `build-essential pkg-config libssl-dev libdbus-1-dev libudev-dev`, and the kit should list them.
4. **GitHub CLI login took three tries (about 13:36 to 14:33; exact times not recorded).** Two device codes expired before approval because the user's passkey was unavailable and they had to use another sign-in method. WSL has no keychain, so `gh` stored the token in plain text.
5. **`fad.testnet` already existed (14:34:40 to 14:34:55).** The faucet command reported `Create Account action tries to create an account with account ID <fad.testnet> which already exists in the storage.` I switched to `fad-pilot1.testnet` (14:35:56 to 14:36:07). Cost: about 1 min. The failed attempt still wrote a useless key file for `fad.testnet`.
6. **Keychain: `near` could not save the key (both create-account runs).** `near` printed `Failed to save the access key ... to the keychain` and fell back to the legacy credentials file `~/.near-credentials/testnet/fad-pilot1.testnet.json`. No keychain service was installed. Fūin signed `seal`, `commit`, `close`, `tee-key` and both `tee-score` steps with that legacy file, so it did not block anything. Nothing was done to make the keychain work.
7. **`fuin check` first run: `✗ near CLI missing` (before 14:51; time not recorded).** Cause: a non-login `bash -c` had no `~/.cargo/bin` on PATH. Fix: I put `~/.cargo/bin` and `~/.local/bin` on PATH for every command (`env PATH=...`). The first-time `uv` environment build ran in the same step (Python 3.15.2 download, 54 packages), which is why the first run took about 2 minutes. `uv` also printed a harmless warning: `build_system.requires = ["uv-build>=0.11.27,<0.12.0"] does not contain the current uv version 0.13.7`.
8. **WSL DNS broke attestation, and the message hid the cause (14:51:29 to 15:07:59, about 16 min to restore).**
   - `fuin run` failed 4 times (Qwen at 14:51:29, 14:52:14, 14:59:50; GLM at 14:55:26) with `need exactly one accepted attestation candidate, got 0`.
   - The kit's message does not say why. The code at `owner.py:82` drops the `outcome` and `error` fields that `check_report` already knows.
   - I read the code, then ran a read-only probe (15:04:11) that showed `evidence_unavailable`: `Intel collateral unavailable: Failed to get collateral: error sending request for url (https://api.trustedservices.intel.com/sgx/certification/v4/pckcrl...)`.
   - `curl` from Windows returned 200. In WSL it failed: `Could not resolve host`. WSL's DNS tunnel (`10.255.255.254`) could not resolve `api.trustedservices.intel.com`, which sits behind a long CNAME chain. `github.com` and `cloud-api.near.ai` resolved normally.
   - Fix: add `[network]` / `generateResolvConf = false` to `/etc/wsl.conf`, write `/etc/resolv.conf` with `nameserver 1.1.1.1` and `nameserver 8.8.8.8` (backups at `/etc/wsl.conf.bak` and `/etc/resolv.conf.bak`), then `wsl --shutdown` (15:07:35). After that the host resolved and the Qwen run succeeded.
   - Suggested kit changes: put `outcome` and `error` in the message at `owner.py:82`, and document that Intel PCS (`api.trustedservices.intel.com`) and NVIDIA NRAS must be reachable.
9. **GLM run stopped after item 0 (15:41:31).** The kit printed `item 1: inference failed 3 times; rerun fuin run to resume`. I reran the same command (resumed 16:09:30). The gap between 15:41 and 16:09 was waiting on the user, not the tool. The certificate warns of `owner-reported failed inference attempts: 4` for GLM and `1` for Qwen.
10. **`fuin status` suggested `fuin reveal` after `close` (checked 16:34).** In a private (TEE) round, nothing is revealed, so the suggestion is wrong. I did not run it. The user says this is fixed in a later kit version.
11. **First verify: Qwen `CAN'T CERTIFY evidence_unavailable` (17:01:10 to 17:05:21).** The failing check was the deployment trace, because an Intel fetch (`.../tdx/certification/v4/qe/identity`) failed. GLM's trace passed in the same run. On rerun, alone, Qwen was `VERIFIED` (17:13:17 to 17:14:58). So it looks transient, but I did not find the cause. It shows that `verify` depends on Intel PCS being reachable.
12. **Not literally run: `unzip` and the glob.** I extracted the zip on Windows (`Expand-Archive`) instead of `unzip`, and gave `verify` both files in one command instead of the shell glob. `unzip` availability in WSL: not recorded.

## Exact commands and packages used for the testnet key under WSL

The key is not in a keychain. `near` saved it to the legacy credentials file (see item 6 above). The setup that led to it:

```sh
curl -LsSf https://astral.sh/uv/install.sh | sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --profile minimal
# GitHub CLI: binary tarball (v2.103.3) copied to ~/.local/bin/gh (no apt, no sudo)
# as root:
apt-get update && apt-get install -y build-essential pkg-config libssl-dev libdbus-1-dev
apt-get install -y libudev-dev
cargo install --locked near-cli-rs
near account create-account sponsor-by-faucet-service fad-pilot1.testnet autogenerate-new-keypair save-to-keychain network-config testnet create
```

No keyring package (for example `gnome-keyring`) was installed. The `libdbus-1-dev` and `libudev-dev` packages were needed to build `near-cli-rs`, not to save the key.
